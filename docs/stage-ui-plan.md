# 단계형 UI 계획서 (전처리 · 솔버 · 후처리) — 초안

작성일: 2026-11-12 · 상태: **단계 A 구현(2026-11-12)** — `src/state/stage.ts`(순수 판정)·`stageRun.ts`(액션 래퍼)·`components/StageBar.tsx`, 테스트 `tests/stage.test.mjs`·Playwright 2건. 자동 심사 분리(B)와 C·D 는 후처리 항목이 실제로 늘어난 뒤 재검토 · 대상: 개발자(Dennis)

구현 메모(A): 표시줄은 현재 탭을 강조하지 않는다(활동 탭이 생성·해석 공용이라 탭↔단계가 1:1 아님). 동적해석은 거부 메시지가 throw 가 아니므로 본문에서 성공/실패를 판정하고, 내부 심사보다 먼저 성공 처리해 심사가 최신으로 남게 했다. 전처리는 실패해도 preEpoch++(Gen 모델이 일부 바뀌었을 수 있음 — 오래됨 쪽으로 판정).
관련 문서: [quantity-takeoff-plan.md](quantity-takeoff-plan.md) (물량 산출 — 이 구조 위에 얹는다)

## 1. 목적

작업을 **전처리 → 솔버 → 후처리** 세 단계로 나누어 사용자가 단계마다 따로 실행·확인하게 한다.
한 번 클릭으로 끝까지 흘러가는 자동화는 지양한다. 각 단계의 상태(미실행/최신/오래됨)를 화면에 보여 주어, 지금 어느 단계이고 무엇을 다시 해야 하는지 알 수 있게 한다.

원칙

- 채팅 입력은 유지한다. 단계 UI는 채팅 명령과 **같은 동작을 화면에서도** 할 수 있게 하는 층이다.
- 액션·엔진 로직은 가능한 한 건드리지 않는다. 경계만 정리한다.
- 기준(TW/CN/KR)별 차이는 기존 `CodeProfile` 훅이 그대로 처리한다.

## 2. 현황 (코드 확인 결과)

| 항목 | 현재 |
|---|---|
| 레이아웃 | 좌: 가이드 + 채팅 / 우: 탭 4개(`logP` 로그, `modelP` 모델, `viewP` 3D, `resP` 결과). `S.panel`이 현재 탭. `src/App.tsx` |
| 전처리 | `actBuildFrame`(`src/actions/model.ts`)가 재료·단면·요소·하중·조합·강성 배율까지 한 번에 입력. 편집 카드 → 계획 카드 확인 → 실행 흐름이 이미 있음 |
| 솔버 | `actAnalyze`(정적) 와 `actDynamic`(질량·고유치·응답스펙트럼, CN/TW RS 주 해석 시 SCALE 재해석 포함) — `src/actions/analysis.ts` |
| 후처리 | `actReview`(심사 지표) 가 **`actDynamic` 끝에서 자동 호출**됨(analysis.ts ~274행). 결과 탭 상단 표 + 채팅 요약 |
| 상태 추적 | `S.buildEpoch`(빌드 횟수)만 있음. 해석이 최신인지, 후처리가 낡았는지 판정하는 상태는 **없음** |
| 채팅 인텐트 | `build`·`analyze`·`dynamic`·`review`·`result` 등이 이미 단계별로 거의 나뉘어 있음 |

핵심 갭: (1) 단계 상태가 없다, (2) 후처리가 솔버에 자동으로 붙어 있다, (3) 후처리 항목(물량·배근)이 늘면 현재 탭 구조로는 담기 어렵다.

## 3. 목표 구조

```
┌──────────────────────────────────────────────────────────────────────┐
│ 헤더: 연결 · 설계기준 · 언어 · 설정                                    │
├──────────────────────────────────────────────────────────────────────┤
│  ① 전처리 ● 최신   ──▶  ② 솔버 ◐ 오래됨   ──▶  ③ 후처리 ○ 미실행     │  ← 단계 표시줄
├───────────────┬──────────────────────────────────────────────────────┤
│  채팅         │  [선택한 단계의 작업 영역]                             │
│  (가이드 포함)│                                                      │
└───────────────┴──────────────────────────────────────────────────────┘
```

상태 표기: `●` 최신 · `◐` 오래됨(앞 단계가 바뀜) · `○` 미실행 · `…` 실행 중 · `!` 실패

| 단계 | 작업 영역 서브탭 | 단독 실행 버튼 | 기존 화면 대응 |
|---|---|---|---|
| ① 전처리 | 편집 카드 · 3D · (개략 물량) | `모델 생성` | 모델 편집 카드, `viewP`, `modelP` |
| ② 솔버 | 실행 · 로그 · 결과(변위·반력·모드) | `해석 실행` (정적/동적/RS 선택) | `logP`, 결과 탭의 반력·변위·부재력·모멘트 |
| ③ 후처리 | 항목별 카드(심사 · 배근 · 물량 …) | 항목마다 `실행` | 결과 탭 상단 심사 표, (신규) 배근·물량 |

③ 후처리는 한 버튼이 아니라 **항목 카드마다 독립 실행**한다. 선행 조건이 없으면 버튼을 비활성화하고 이유를 표시한다(예: "해석 필요").

## 4. 단계 상태 모델

### 4.1 상태 저장 (`src/state/store.ts`)

각 단계가 "무엇을 기준으로 만들어졌는지"를 카운터로 기록해 낡음을 계산한다. 불리언 플래그를 직접 뒤집지 않는다.

```ts
stage: {
  pre:   { done: boolean, epoch: number }          // 모델 생성/편집이 일어날 때마다 epoch++
  solve: { done: boolean, basedOnPre: number, kind: 'static'|'dynamic'|'rs'|null, running: boolean, error?: string }
  post:  { [item in 'review'|'rebar'|'quantity']?: { done: boolean, basedOnSolve: number } }
  solveEpoch: number                                // 해석이 성공할 때마다 ++
}
```

판정(순수 함수 `stageStatus(stage)` — 단위 테스트 대상)

- 전처리: `done` 이면 최신. (Gen 쪽 변경은 앱이 알 수 없음 — 6절 위험 참조)
- 솔버: `done && basedOnPre === pre.epoch` 이면 최신, `done` 이지만 epoch 다르면 오래됨, 아니면 미실행.
- 후처리 항목: `done && basedOnSolve === solveEpoch` 이면 최신, 아니면 오래됨/미실행. 단 개략 물량처럼 해석이 필요 없는 항목은 `basedOnPre` 를 쓴다.

### 4.2 무효화 규칙 (v1은 단순하게)

| 일어난 일 | 전처리 | 솔버 | 후처리 |
|---|---|---|---|
| 모델 생성/재생성(`actBuildFrame`) | epoch++ | 오래됨 | 오래됨 |
| 모델 편집(`modify_section`·`resize_subset`·`add_load`·`add_bracing`·스펙 갱신) | epoch++ | 오래됨 | 오래됨 |
| 해석 실행 성공 | — | 최신(`solveEpoch++`) | 오래됨 |
| 후처리 항목 실행 | — | — | 해당 항목 최신 |
| 모델 비우기(`clear`) | 초기화 | 초기화 | 초기화 |

v1은 "앞 단계가 바뀌면 뒤 단계 전부 오래됨"으로 단순하게 시작한다. 입력별 세분(지진 입력만 바꾸면 솔버만 무효 등)은 v2 이후 필요가 확인되면 한다.

기록 지점은 이미 `notify()` 직전에 상태를 바꾸는 액션들이다. 새 상태를 갱신하는 호출을 액션 끝에 추가하는 방식이며, 액션 로직 자체는 바꾸지 않는다.

## 5. 후처리 분리 (동작 변경 포함)

- `actDynamic` 끝의 자동 `actReview` 호출을 제거하고 ③ 후처리의 `심사 지표` 카드로 옮긴다.
- 결과 메시지에는 "심사 지표는 후처리에서 실행" 안내와 [실행] 링크만 남긴다.
- **사용자 눈에 보이는 변경**이므로 릴리즈 노트에 명시한다. 기존 습관을 위해 설정에 "해석 후 자동 심사" 옵션(기본 끔)을 둘지는 열린 결정(7절).
- LLM 도구 `run_dynamic` 의 반환 내용과 `review_indicators` 호출 순서도 맞춰 수정한다(시스템 프롬프트에 단계 설명 추가).

## 6. 구현 단계 (제안)

릴리즈를 쪼개서 한 번에 큰 변경이 들어가지 않게 한다.

### 단계 A — 상태와 표시줄 (minor)

- `S.stage` 와 `stageStatus` 순수 함수, 무효화 호출 지점 연결.
- 우측 패널 위에 **단계 표시줄** 추가(`src/components/StageBar.tsx`). 클릭 시 해당 단계의 기본 탭으로 이동.
- 탭 구조는 그대로 둔다(기존 `logP/modelP/viewP/resP` 유지). 표시줄은 탭 이동의 바로가기 + 상태 표시 역할.
- i18n 4개 언어, 접근성(`role=tablist`/`aria-current`, 상태는 색뿐 아니라 아이콘·텍스트 병기).
- 이 단계에서는 자동 심사 분리를 하지 않는다.

### 단계 B — 후처리 분리 (minor)

- `actReview` 자동 호출 제거, ③ 후처리 영역과 항목 카드 도입(처음에는 `심사 지표` 카드 하나).
- 결과 탭 상단의 심사 표를 후처리 영역으로 이동.
- 인텐트 `review` 는 후처리 영역으로 이동하며 실행. LLM 도구 설명 갱신.
- 여기에 물량 산출 1단계 카드를 붙일 수 있다(quantity-takeoff-plan 1단계).

### 단계 C — 탭 재배치 (minor)

- 우측 탭을 단계별 작업 영역으로 재구성: ① 전처리(편집 카드·3D), ② 솔버(실행·로그·결과), ③ 후처리(항목 카드).
- 좁은 화면: 표시줄이 상단 탭이 되고 채팅은 별도 탭.
- 가이드 패널의 항목을 자기 단계로 안내(클릭 = 입력창에 타이핑 후 실행하는 기존 방식 유지).

### 단계 D — 후처리 항목 확장

- 배근 설계, 정확 물량 카드 추가(quantity-takeoff-plan 2·3단계). 선행 조건·오래됨 표시를 이 카드들이 그대로 사용한다.

## 7. 열린 결정

1. **무효화 세분 여부** — v1 단순 규칙으로 시작할지(권장), 처음부터 입력별로 세분할지.
2. **자동 심사 옵션** — 기본 끔 + 설정 옵션을 둘지, 아예 제거할지.
3. **탭 재배치 시점** — 단계 A에서 표시줄만 먼저 넣고 재배치는 C에서(권장), 처음부터 같이 할지.
4. **실행 중 상태의 취소** — 해석은 최대 15분 타임아웃인데 취소 버튼이 필요한지(현재 없음).
5. **Gen 외부 변경 처리** — 사용자가 Gen GUI에서 직접 모델을 바꾸거나 DCON을 바꾸면 앱은 알 수 없다. `다시 확인` 버튼(모델 요약/해석 결과 존재 여부 조회)으로 상태를 재동기화할지.

## 8. 위험과 대응

| 위험 | 대응 |
|---|---|
| 낡음 판정 오류(잘못 "최신"으로 표시) | 순수 함수로 분리하고 Vitest로 전이표를 전수 검증. 의심스러우면 "오래됨" 쪽으로 판정 |

| 채팅 중심 사용자의 흐름 변화 | 단계 A는 탭 그대로 유지, 자동 심사 제거는 B에서 릴리즈 노트에 명시 |

| 동시 실행 | `S.busy` 와 `stage.solve.running` 으로 중복 실행 차단. 실행 중에는 앞 단계 편집 버튼 비활성 |

## 9. 검증

- Vitest: `stageStatus` 전이표(모든 무효화 경로), 액션 호출 후 `S.stage` 갱신(가짜 MIDAS 하네스 `tests/_harness.mjs` 활용).
- Playwright(`npm run test:ui`): 표시줄 상태 전이(빌드 → 해석 → 심사 → 모델 편집 시 오래됨 표시), 선행 조건 없는 카드의 비활성 버튼, 모바일 폭.
- 라이브(Gen NX 단독 사용): 전처리 → 솔버 → 후처리를 각각 따로 실행해 결과가 기존 한 번에 실행한 값과 같은지 확인(회귀).
- i18n: 키 추가 후 `npm run i18n:check -- --write`, `tests/i18n.golden.json` 해시·키 개수 갱신.
