# 스틸 프레임 Agent — 분리 앱 계획서 (초안)

작성일 2026-10-19 · 작성 배경: RC구조물 Agent(v3.12.1)에 스틸을 넣으면 앱 목적(RC)이 흐려지고 로드맵이 밀리므로, **별도 앱**으로 분리하는 안을 정리한다.
상태: 초안. 수요·범위가 확인되기 전에는 착수하지 않는다.

---

## 1. 목적과 범위

| 항목 | 내용 |
|---|---|
| 제품 | MIDAS Gen NX Open API로 **강구조 골조를 자동 모델링·해석**하고 설계기준별 검토 지표를 보여주는 웹 도구 (RC구조물 Agent의 자매 앱) |
| 이름(가칭) | 스틸구조물 Agent |
| 범위(1차) | 모멘트골조(SMF) + 가새골조(CBF) 해석까지. RC 앱의 "해석 범위" 수준과 동일 |
| 범위 밖(1차) | 접합부 상세 설계, 합성보·데크 설계, 부재 단면 최적화, 도면, 내화 설계 |
| 설계기준 | **1차 = 대만(TW) 하나**. 이후 KR → CN 순으로 확장 (기준 선택은 RC 앱과 같은 프로필 구조) |
| 비목표 | RC 앱 기능 변경, 두 앱의 화면 통합 |

**원칙**: RC 앱은 건드리지 않는다. 스틸 앱이 필요한 것만 가져가고, 기준 의존 로직은 `CodeProfile`로 격리한다.

## 2. 먼저 확인할 것 (착수 전 게이트)

아래가 확인되기 전에는 구현에 들어가지 않는다.

1. **수요 확인**: 구체적 사용 사례(고객·프로젝트), 대상 기준, 해석만인지 설계 검토까지인지.
2. **Gen NX 강재 API 라이브 확인** (RC 앱에서 해온 방식과 동일하게 단독 사용 시간에):
   - 강재 재료: `db/MATL` TYPE STEEL, 기준별 DB 이름(TW SN400·SN490 / KR SS275·SM355 / CN Q235·Q355)과 수용 여부
   - H형강·박스·파이프 단면: DB 규격 단면 등록 방식 vs 사용자 정의(`DBUSER`)
   - 가새(truss/tension-only/일반 beam) 요소 입력 방식
   - 강재 설계 코드(`DCON`) 이름과 수용 여부
   - 강재는 균열 보정이 없으므로 `ESSF`(강성 배율)는 불필요한지, 단면 방향(강축·약축) 규약
   - 슬래브/데크 하중 전달: 바닥하중(FBLD)+보 분배가 강재 보에서도 동일하게 동작하는지
3. **규범 원문 KB**: TW 鋼構造極限設計法規範 및 해설, 耐震規範의 강구조 시스템 항목(R·Fu, 표1-3)을 KB로 확보. (RC 앱의 KB는 RC 규범 위주라 그대로는 부족)
4. **Gen NX 공유 사용 문제**: 다른 클라이언트와 동시 사용 시 라이브 검증이 깨진다 → 검증 일정은 단독 사용 시간으로.

## 3. 아키텍처 — 공유 vs 복제

### 3.1 방식 비교

| 방식 | 장점 | 단점 | 판단 |
|---|---|---|---|
| A. 저장소 복제(fork) 후 분기 | 가장 빠르게 시작, RC 앱 무영향 | 공통 코드 수정이 두 곳에 필요, 시간이 갈수록 어긋남 | **1차 채택** |
| B. 공통 패키지 추출(monorepo) | 중복 없음 | RC 앱 리팩터 필요 → 리스크, 일정 지연 | 스틸 앱이 안정된 뒤 검토 |
| C. 한 앱에 모드 추가 | 중복 없음 | RC 앱 목적 훼손, 분기 폭증, 회귀 검증 2배 | 비채택 |

**결정**: A로 시작한다. 단, 공유 후보 모듈은 처음부터 "나중에 패키지로 뺄 수 있게" 경계를 지켜 복사한다(수정은 스틸 앱 쪽에서만).

### 3.2 재사용 / 새로 작성 구분

| 모듈 | 처리 | 비고 |
|---|---|---|
| `src/mapi/client.ts` (Gen NX 연결) | 그대로 복사 | midas-nx SDK 래퍼, MAPI-Key 메모리 보관 규칙 유지 |
| `src/state/` (store·ui) | 복사 후 필드 정리 | 모델 상태에서 RC 전용 필드 제거 |
| `src/components/` (Header·Chat·Drawers·View3D·Panels·ReleaseNotes) | 복사 + 문구 교체 | View3D는 부재를 선으로 그리므로 형상 무관, 그대로 사용 가능 |
| `src/agent/` (parse·local·llm·session·editor·plan) | 복사 후 스틸 용어로 수정 | NLP 정규식·LLM 도구 스키마는 프로필 `fields`에서 생성되므로 수정 범위 작음 |
| `src/actions/` (model·analysis·review) | 복사 후 대폭 수정 | 단면/재료/자중/조합 부분이 스틸용으로 바뀜 |
| `src/codes/` 프로필 구조(`types.ts`, 훅 체계) | 구조만 복사, 내용은 새로 작성 | RC 계수·식은 가져오지 않음 |
| `src/codes/tw.ts` 중 지진·풍 하중 산정 | **부분 재사용** | 하중(V, 층력, 풍압)은 구조 재료와 무관한 부분이 많음. 단 R·Fu·T 식은 강구조 값으로 교체 |
| `shared/rc_engine.js` | 복사 후 필요한 함수만 남김 | RC 설계(배근·PM 곡선) 제거. 격자·층고·층 데이터 생성은 재사용 |
| `shared/i18n.js` | 복사 후 정리 | RC 문구 제거, 스틸 문구 추가, 4개 언어 유지 |
| 릴리즈 방식(`scripts/release*.mjs`, 릴리즈 노트 4개 언어) | 그대로 복사 | 버전은 스틸 앱 자체 1.0.0부터 |
| `tests/_harness.mjs` | 복사 | 스틸용 테스트는 새로 작성 |

### 3.3 새로 작성해야 하는 핵심

- **스펙 모델**: 단면 팔레트의 `shape`(H/BOX/PIPE), 강종 카탈로그, 가새 배치.
- **강재 프로필 훅**: 재료(강종·E·Fy·단위중량 77kN/m³), 단면 등록, 자중, 조합, 시스템 표(R, Ω0, Cd, 높이제한), 층력, 검토 지표.
- **가새 골조 템플릿**: 가새 위치·형식(X, V, 역V, 편심가새)을 격자에서 배치.
- **자동 단면 선택**(`prepareNew`): 압축·휨·층간변위 기준으로 H형강 규격 선택. 규격 표(H형강 DB)는 데이터 파일로.

## 4. 프로필 설계 (TW 1차)

RC 앱의 `CodeProfile` 훅을 그대로 쓰되 내용을 교체한다.

| 훅 | 스틸(TW) 내용 |
|---|---|
| 재료 카탈로그 | SN400B/C, SN490B/C (Fy, Fu, E=200GPa) |
| 단면 | H형강 규격 표(예: H400×200×8×13), 박스, 파이프. 약축·강축 방향 규약 |
| 자중 | 부재 77kN/m³ + 바닥 SDL(데크·마감·내화피복) |
| 하중조합 | 鋼構造極限設計法規範의 조합(LRFD). 원문 확인 후 확정 |
| 지진 | 耐震規範 2.2 V 식 재사용, **R·Fu 는 강구조 시스템 값**(SMF, CBF, EBF 별) |
| 풍 | 耐風規範 2014 그대로 재사용 |
| 검토 지표 | 층간변위각 ≤0.005, 비틀림 1.2, 연층, 질량비, P-Δ θ(2.13), 강기둥-약보 지표(SCWB), 가새 세장비 |
| 균열단면 | 없음(총단면 강성) |
| 기둥/보 자동 선택 | 축력·휨 기반 H형강 선택, 변위 기준으로 보정 |

## 5. 단계별 계획

| 단계 | 내용 | 산출물 | 완료 기준 |
|---|---|---|---|
| 0 | 게이트 확인(2장) — 수요, 강재 API 라이브, KB 확보 | 확인 보고서(`MAPI_FINDINGS` 형식) | 강재 재료·단면·가새·DCON 입력이 Gen NX에서 수용됨 |
| 1 | 저장소 복제·정리 — RC 전용 코드 제거, 이름·버전 초기화, 빌드·배포 연결 | 빈 껍데기 앱(연결·채팅·3D 동작) | 로컬 빌드 통과, Vercel 프로젝트 별도 생성 |
| 2 | 스펙·모델링 — 강재 재료·H형강 단면·모멘트골조 생성 | 모멘트골조 모델 생성 | Gen NX 라이브: 부재·자중·바닥하중이 앱 산정과 일치 |
| 3 | TW 하중·조합·해석 — 지진/풍 층력, 조합, 정적+동적(RS) | 해석 실행·결과 표 | 독립 재구현 테스트 + 라이브: 층중량·밑면전단 일치 |
| 4 | 가새골조 — 템플릿, 가새 요소, 가새 포함 해석 | CBF 모델 | 라이브: 가새 축력 방향·강성 확인 |
| 5 | 자동 단면 선택 + 검토 지표 | `prepareNew`, 심사 패널 | 대표 모델(10층 사무)에서 지표 값 확인 |
| 6 | 4개 언어·가이드·테스트·릴리즈 | v1.0.0 | `npm test`, 라이브 회귀, 릴리즈 노트 4개 언어 |
| 7(후속) | KR 기준 추가 → CN | v1.x | 기준별 원문 대조·라이브 확인 |

각 단계는 RC 앱과 같은 규칙으로 진행한다: 구조가 바뀌는 단계는 Gen NX 라이브 검증, 식은 테스트 안에서 원문대로 독립 재구현, 사용자에게 보이는 변경마다 버전과 4개 언어 노트.

## 6. 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 강재 API 입력 방식이 예상과 다름(규격 DB 이름, 가새 요소 등) | 단계 2~4 지연 | 단계 0에서 먼저 확인, 실패 시 사용자 정의 단면으로 우회 |
| 강구조 규범 원문 부족 | 조합·R값 근거 약화 | KB 확보 전에는 해당 항목을 `unverified` 표시, 구현 보류 |
| 복제 후 RC 앱과 공통 코드가 어긋남 | 유지보수 중복 | 공통 모듈 목록을 문서화, 나중에 패키지 추출(방식 B) 검토 |
| Gen NX 공유 사용으로 라이브 검증이 깨짐 | 검증 신뢰 저하 | 단독 사용 시간에만 검증, 결과 기록 |
| 범위 확대(접합부·합성보·설계 검토) | 일정 폭증 | 1차는 해석까지로 고정, 이후는 별도 기획 |
| 2개 앱 운영 부담 | 인력 분산 | RC 앱 로드맵을 우선하고 스틸은 수요가 확인된 뒤 착수 |

## 7. 결정이 필요한 사항 (사용자 확인 요청)

1. 스틸이 필요한 구체적 사례가 있는가? (없으면 착수 보류)
2. 1차 기준: TW로 시작해도 되는가?
3. 1차 범위: 해석까지(모멘트골조+가새골조)로 고정해도 되는가?
4. 저장소·배포: 새 GitHub 저장소와 별도 Vercel 프로젝트로 할 것인가, 아니면 같은 저장소의 다른 브랜치/폴더로 할 것인가?
5. 앱 이름과 도메인.

## 8. 일정 (참고)

일정은 단계 0 결과에 크게 좌우되므로 확정하지 않는다. 단계 0 확인을 끝낸 뒤 단계 1~3의 소요를 다시 추정한다.
