# 물량 산출 계획서 (초안)

작성일: 2026-11-12 · 상태: **보류** (2026-11-12 결정 — 대만 외부 계산서 대조가 끝난 뒤 경로 B(Gen 배근 읽기)부터 재개. 배근률 개략 산정은 만들지 않음) · 대상: 개발자(Dennis)

## 1. 목적

모델에서 **콘크리트·거푸집·철근 물량**을 산출해 결과 탭에 보여 준다. 두 가지 값을 나란히 제공한다.

- **개략 물량** — 배근률(kg/m³)로 철근량을 추정. 해석·설계 없이 모델 형상만으로 즉시 산출.
- **정확 물량** — 배근 설계 결과(주근·늑근 실제 배근)로 산정. 개략값과 비교해 개략 배근률의 적정성도 확인.

## 2. 현황 (코드 확인 결과)

| 항목 | 상태 |
|---|---|

| 배근 설계 엔진 | `src/engine/design.ts`의 `rcBeamDesign`·`rcColumnDesign` 존재(TW 112 기준). **현재 React 앱에서 호출하는 곳 없음**(Wizard 시절 코드) |

결론: 개략 물량은 바로 가능. 정확 물량은 **설계 파이프라인이 선행 조건**이며, 이는 물량 기능과 별개의 큰 작업이다.

## 3. 단계 계획

### 1단계 — 개략 물량 (전 기준 공통)

**산출 항목** (층별 소계 + 총계, 동별 구분 가능)

| 항목 | 단위 | 산정 방법 |
|---|---|---|
| 콘크리트 | m³ | 기둥 H×B×길이, 보 H×B×길이(벽 위 `inWall` 보는 벽에 포함되므로 제외), 벽 두께×폭×높이, 바닥 슬래브 `slabThk`×면적 |
| 거푸집 | m² | 기둥 둘레×길이, 보 (바닥 B + 양측 2×(H−슬래브 두께))×길이, 벽 양면, 슬래브 하면 + 가장자리 |
| 철근 | t | 콘크리트 체적 × 부재유형별 배근률(kg/m³) |

- 재료(콘크리트 강도)가 구역별로 다르면 강도별로 분리해 집계한다(팔레트 `storyAssign` 활용).
- 겹치는 체적(보-기둥 접합부 등)은 1단계에서는 중복 공제하지 않고 "개략"이라고 명시한다. 공제 규칙은 후속 항목.
- 지하층·옥상 구분은 `deriveFloorGroups`의 `role`을 사용한다.

**철근 개략 배근률**

- 부재유형 4종: 기둥 / 보 / 슬래브 / 벽(코어·내력벽).
- 기본값은 기준별 프로필(`CodeProfile`)에 두고 편집 카드 또는 결과 탭에서 사용자가 바꿀 수 있게 한다.
- **기본값은 사용자 확인이 필요하다.** 실무 통상 범위를 잠정값으로 쓰되 화면에 "개략 가정"으로 표시한다. 사내 기준값이 있으면 그것으로 대체한다.
- 지진 설계범주·층 위치(저층 기둥은 배근률 높음)에 따른 보정은 후속 항목.

**구현 위치(안)**

- `src/engine/quantity.ts` — 순수 함수 `takeoff(spec, rates)` → `{ byStory[], total, byMaterial[] }`. 브라우저 전역 없음, `modelDeadWeights`와 같은 부재 순회 방식.
- `src/state/store.ts` — `S.quantity`(결과), `S.quantityRates`(배근률 편집값).
- `src/components/Panels.tsx` — 결과 탭에 '물량' 표 추가(또는 별도 탭).
- 인텐트 `quantity`(물량/用量/quantity) + LLM 도구 `get_quantity` — 기존 `review` 인텐트·`get_review` 패턴을 따른다.
- i18n: ko/en/zh-TW/zh-CN 동시 추가 후 `npm run i18n:check -- --write`, `tests/i18n.golden.json` 해시 재생성.

**검증**

- Vitest: 단일 기둥/보/슬래브의 손계산 값과 비교(독립 재구현), 2동·코어·내력벽 케이스, `inWall` 보 제외.
- 자중 일관성 교차검증: `체적 × 단위중량`이 `modelDeadWeights`의 부재 자중 합과 일치해야 한다(같은 출처 확인).
- Playwright: 결과 탭 표 표시, 배근률 변경 시 철근량 갱신.

### 2단계 — 설계 파이프라인 (TW 한정, 별도 계획서 필요)

- 해석 후 BEAMFORCE 등에서 부재력 회수 → 부재군(층 그룹×단면)별 최대 요구력 집계 → `rcBeamDesign`·`rcColumnDesign` 실행 → 결과를 `S.design`에 저장.
- Gen DCON을 쓸지 앱 엔진을 쓸지 결정해야 한다. 우리 CLAUDE.md 기록은 POST/PM 라이브 곡선이 `db/RCHK` 404이고 GUI RC Design 선행이 필요하다는 것이다. 반면 Rebar-repair 기록(2026-10-14)은 보·기둥·벽·가새 `*-ANAL` + `*-TABLE` 검토가 TW(`TWN-USD112`)·KR·CN 세 기준에서 현재 빌드로 모두 동작한다고 한다. **두 기록이 다른 기능(곡선 vs 검토표)을 말하는지 먼저 라이브로 확인한다.**
- Gen 검토(`*-TABLE`)를 쓰면 CN·KR도 판정은 가능해진다. 다만 요구 배근량을 산정하는 설계가 아니라 입력한 배근의 OK/NG 검토이므로, 배근 산정 자체는 앱 엔진이 맡는다.
- 다중 단면은 대표 단면 기준이라는 기존 경계를 유지할지, 부재군별로 확장할지 결정이 필요하다.
- 이 단계는 물량 기능의 선행 조건일 뿐 아니라 배근·도면 기능의 공통 기반이다.

### 3단계 — 정확 물량

**입력 경로를 둘로 둔다.**

- **A. 앱 설계 결과** — 2단계 파이프라인의 `S.design`. TW만.
- **B. Gen에 입력된 배근** — Gen REBB(보)·REBC(기둥)·REBR(가새)·REBW(벽)를 읽어 계산. 사용자가 GUI에서 배근했거나 Rebar-repair로 수정한 모델에도 적용되고, 기준 제약이 약해 CN·KR도 가능하다. REB*는 단면 번호 기준(벽은 Wall ID)이므로 같은 단면을 쓰는 요소 전체에 적용하고, 배근이 비어 있는 단면은 개략 배근률로 대체하며 표시한다.

두 경로 모두 아래 길이 산정 규칙을 공유한다.

- 보: 상·하부 주근 본수×직경×(스팬 + 정착·겹침 길이) + 늑근(간격 s로 개수 산정, 둘레 길이 − 피복).
- 기둥: 주근 본수×직경×(층고 + 겹침) + 띠철근.
- 슬래브·벽: 설계 엔진이 없으면 개략 배근률 유지(정확 물량에서도 해당 항목은 "개략" 표시).
- 철근 중량 = 길이 × 단위중량. 단위중량·직경 표는 Rebar-repair `rcCodePresets.ts`(기준별 철근 규격)를 이식한다. 철근 라벨은 모델 파일마다 다르다(KS `D19`, 영국식 `P20`, GB 소문자 `d20`). 라벨→직경 변환은 해당 모델 DB 우선, 없으면 전체 DB 폴백으로 처리한다.
- 정착·겹침 길이는 Rebar-repair `twDevLength.ts`를 이식한다(TW 112년 규범 25.4.2.3·25.4.9.2·25.5.2.1·25.4.3 원문에서 읽고 標準圖 RC02 표와 셀 단위 대조, 단위 테스트 포함). 표준 조건값(에폭시·경량 보정 없음)이라는 가정도 함께 가져온다. KR·CN은 해당 규범 정착 규칙을 같은 형식으로 추가해야 하며, 그 전에는 경로 B에서도 TW 외 기준은 개략 길이 가정(주근 길이 + 고정 배수)을 쓰고 "개략"으로 표시한다.
- 개략 vs 정확 비교 표: 부재유형별 kg/m³ 차이를 보여 주어 개략 배근률 보정 근거로 쓴다.
- 설계 결과가 없거나 `over`(설계 불충족) 부재가 있으면 해당 값에 경고를 표시한다.

## 3.5 참고 저장소: Rebar-repair (이식 계획)

`E:\AI Study\Rebar-repair`(QuickRebar NX, Gen NX 배근 수정 웹앱)에서 가져올 자산. 별도 저장소이므로 **의존성이 아니라 복사 이식**하고, 파일 머리 주석에 출처 경로와 이식 날짜를 남긴다. 원본이 갱신되면 수동으로 비교한다.

| 원본 | 내용 | 용도 | 단계 |
|---|---|---|---|
| `src/lib/twDevLength.ts` (+ `__tests__/twDevLength.test.ts`) | TW 정착·겹침·압축 정착·갈고리 길이 | 정확 물량 길이 산정 | 3 |

이식하지 않는 것: React 컴포넌트·3D 뷰어(스타일 체계가 다름), 백엔드 `api/*`(서버리스 프록시 구조).

이식 시 지킬 점

- 단위계: Rebar-repair 정착 길이는 kgf/cm²·cm, 우리 엔진은 MPa·mm가 섞여 있다. 어댑터 함수 한 곳에서 변환하고 단위 테스트로 고정한다.
- 이식한 상수·식은 우리 저장소에서도 테스트로 고정한다(원문 대조는 원본에서 끝났으므로 이식 시 회귀만 막는다).
- 설계 코드 계수는 기준별로 검증된 것만 가져온다(원본 주석에 검증 근거가 있는 것).

## 5. 위험과 결정 필요 사항

1. **개략 배근률 기본값** — 근거 있는 사내 기준 필요. 없으면 잠정값 + 화면 표시.
2. **중복 체적 공제 방식** — 개략은 미공제로 시작, 정확도 요구 시 공제 규칙 추가.
3. **2단계 경로**(DCON vs 앱 엔진) — 별도 라이브 확인 후 결정. 우리 기록(POST/PM 곡선 404)과 Rebar-repair 기록(`*-ANAL`/`*-TABLE` 동작)이 다르므로 어느 기능을 가리키는지 먼저 확인한다.
4. **기준별 노출** — 정확 물량은 TW만 활성, CN·KR은 개략 전용임을 UI에서 명확히.
5. **경로 B 데이터 품질** — Gen에 배근이 비어 있거나 부분 입력된 모델, 모델 철근 DB 라벨이 다른 경우(`Wrong Field`)의 처리. 비어 있는 단면은 개략값으로 대체하고 화면에 구분 표시한다.
6. **저장소 간 중복** — 이식한 정착 길이·규격 표가 원본과 갈라질 수 있다. 출처 주석과 회귀 테스트로 관리한다.
7. **기존 모델 호환** — 물량은 `spec`에서 재계산하므로 저장 상태 변경 없음.

- 2단계: 별도 계획서 작성 후 진행.
